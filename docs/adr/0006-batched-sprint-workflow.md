# ADR-0006：小批连续开发、自动技术出口与48小时冲刺

Status: Accepted
普通批内连续实现、跨批环境复用及原量化性能契约已由[ADR-0010](0010-selected-scope-and-lean-workflow.md)修订。下文原每件先审/每批新环境和1.20/1.30保证保留为历史；四槽与自动/人工出口规则继续有效。
日期：2026-11-10
决定来源：用户确认全量功能与自动验收、人工体验单列、连续48小时且质量优先、普通同领域2–3票合批、四个代理名额，以及本地耗时与内存阈值；本轮明确仅落实执行约定和计划。

## 生效范围

本决定覆盖项目执行层的逐票新代理约定，补充ADR-0002的工程记录规则和ADR-0004的人工验收时点。ADR-0001的迁移范围、ADR-0003的未知结果不重放、ADR-0005的运行时与存储契约继续适用。

编制本决定时仅授权文档、计划与任务图调整；实际启动指令、t0（Asia/Shanghai）、集成SHA、在途任务与停止边界统一保存在实施进度。用户明确启动后按其记录派发产品工作，新的明确指令优先于历史停止安排。计划文件、接续模板及经过48小时均不构成启动、费用或实验授权。

## 小批与独立验收

- 普通同领域任务按2–3票组成一批；存储、权限、取消、恢复、沙箱等关键边界采用单票或更小的可独立验收单元。领域责任包用于归属，批次用于调度，两者都不替代任务图。
- 每个新批次使用独立实现上下文、分支及worktree，从包含工程记录的已提交集成tip开始。批内可复用负责人、上下文和环境；已有在途任务保留原分支、负责人及未提交材料，由主协调核实后接续。
- 每票继续读取来源、TDD、保存独立预期、提交与证据。链式依赖在接缝处小提交，由独立审查者复验、集成并按票完成条件结题后，才实施下一票。无依赖且均已解锁的票可以一起送审。批末一次审查不能提前解锁批内后票。
- 维持单一集成分支。主协调维护公共状态、对应表和矩阵；实现者交付候选与资源回执，未参与该候选实现的审查者在独立worktree复验。失败退回修复并保留失败证据。
- 原始参考技能、许可、来源及hash保持原样；项目适配只写在本地工作流和本决定中。批次记录必须随代码和工程记录提交，创建后续worktree前确认所需记录已经入库。

完成条件：每张结题票各自满足完整验收条件、独立复核通过且已集成；批次结束不推定票或母案例族通过。

## 四个名额与调度

常态为主协调、两个实现者、一个独立审查者，共四个活跃名额。主协调负责接口、共享文件归属、依赖和集成；审查队列为空时可临时增加一路实现，出现待审候选时释放名额给新的独立审查上下文，实现者不审自己的候选。最终并行审查同样计入这四个名额。

按实际依赖解锁，优先能解除最多关键后继的候选。审查积压达到两批时暂停派发新实现，先审查和修复。共享入口、注册表、StoragePort和事件结构同一时段只由一个明确负责人修改；更换负责人前交付接口、SHA和未决项。

每批记录领取、首个可跑候选、送审、复核结束、集成时间，以及准备、执行、阻塞、返工时间和资源状态。每4小时检查已集成结果、首次审查通过率、待审/待修/外部阻塞；第12小时重算剩余实现、审查、串行链和最终门禁所需时间。48小时是冲刺目标，未通过则据实继续修复。

## 自动技术出口与人工出口

产品状态仍以验收矩阵及其子案例为准。77/78票增加`Automatic exit`与`Automatic evidence`两个汇总字段，取值为`pending / failed / passed`和可追溯证据指针。`passed`要求本票所有可自动验证的产品技术子案例通过、独立复核、候选已集成，且矩阵逐项记录相同commit、case/subcase和证据；不是把尚需用户操作的案例填为通过。

| 票 | 自动技术出口 | 人工出口 |
| --- | --- | --- |
| 77 | 已覆盖产品路径的终端状态、内容、取消、恢复等可自动检查项，含真实Windows路径的技术证据 | 用户实际中文IME、连续缩放、粘贴、面板和画面体验等WT-01..09待验项 |
| 78 | 实际Windows凭据、定时、进程树、ACL/持久化、沙箱、电源、通知、剪贴板等可自动执行的组合证据；不能用模拟端口代替 | 需用户操作、登录/重启及主观反馈的对应子项，按既定支持范围留证 |

自动技术出口通过、人工仍未验时，77/78可为`awaiting-user`，用户体验仍为`pending`；完整结题继续要求ADR-0004的用户实际验收。85另有77/78的完整票依赖，其最终交付必须等人工`accepted`，不消费两票的自动出口替代完整验收。

79对78、84对77的目标依赖语义是只消费自动技术出口。保留原`deps`硬边，在任务图用`dependency_exits`分别声明`{"wincaps": "automatic"}`、`{"wtaccept": "automatic"}`。声明本身不是放行结果；驱动适配与独立验证进度见实施记录，完成前仍按`resolved`保守判断，主协调也按此规则执行。

依赖工具适配时须同时满足：仅识别已声明的自动边；核验出口、集成commit、矩阵与复核证据；其它普通依赖及D节点仍按原门禁；缺字段、未知值、缺证据或不一致均保持阻塞；85始终检查77/78完整结题与用户accepted。具体位置和反例见[冲刺计划](../../.scratch/ruocun/sprint-48h.md)。

完成条件：“完整实现与自动门禁完成、人工待验”和“全部84票完成、交付accepted”分别报告；前者不自动关闭77/78/85，也不把未运行的技术门禁排除在外。

## 性能契约

同机、同输入、同工作量对照唯一冻结DAO快照；来源运行使用独立受控副本。功能输出、兼容性、稳定性、顺序、并发、权限及持久确认要求保持。

| 子案例 | 固定工作量 |
| --- | --- |
| PKG-07.perf-startup | 启动到对应可用状态，冷启动与预热结果分列 |
| PKG-07.perf-dispatch | 固定本机SSE/工具批回放，比较事件处理和工具调度 |
| PKG-07.perf-store | 相同消息和工具结果数量的提交、退出与恢复 |
| PKG-07.perf-terminal | 相同终端历史和流式压力下的输入处理与渲染 |

逐场景本地耗时比不超过1.20，受管进程树同一时刻聚合峰值内存比不超过1.30。预热场景先预热3次，再正式20次，来源与目标交错运行；冷启动20次单列。记录中位数、p95和原始样本，耗时阈值按每场景中位数判定；内存按对应场景20次进程树峰值的最大值之比判定，同时报告峰值分布。明显输入卡顿、取消失效和稳定性故障按功能门禁处理，不能用统计平均抵消。

模型网络等待与真实任务端到端结果另列。近零耗时批量重复到可稳定计量；基线为零/无对应行为、噪声过大或无法同条件测量时标为未验证并补充有依据的对照，不能直接记通过。接近阈值时复测，保留所有样本；来源没有的Windows补齐能力验证功能要求，不伪造DAO性能比值。

## 执行边界与记录

性能指标归入PKG-07子案例，不另造来源案例族。规格、矩阵、相关票只引用本决定；计划维护批次、文件归属与检查点，任务票和矩阵继续维护真实状态。

环境白名单、合成HOME/配置/会话、日志脱敏和资源回执继续执行。公开依赖缓存可按hash只读复用，私密状态各批隔离。真实模型沿已明确账户、参数与费用上限；缺少具体预算时集中说明并继续独立工作，本决定不增加费用授权。07异常探针和D22历史材料的停止要求继续有效，重新实验须遵守对应事件记录与真实门禁。
