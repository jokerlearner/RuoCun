## 推荐方案 A：迁移核心压缩策略，沿用现有会话存储

1. **统一压力测量。** 在请求前衡量当前材料，计入系统提示、工具定义、新增消息和可支持的图片估算；保留 API 实际用量与粗估的区别。触发策略参考上游 80% 窗口与输出预留/额外余量的较小值。上游 65,536 token 余量不得不分模型地套用到小窗口；参数必须校验，具体默认按 RuoCun 实际模型容量落地。
2. **先做确定性工具文本裁剪，再测量。** 只有已确认压力且原结果能够从既有记录或 spill 恢复时，才缩短过大普通工具正文；保留头、尾、原文读取线索和工具身份。裁剪已足够则不请求摘要。恢复代码消费的 TaskWait/后台投递等控制结果不裁剪；不改变工具账本。裁剪先在候选副本完成：若还需摘要，两步均成功才一次提交；避免摘要失败时裁剪结果已改变原上下文。
3. **只摘要较旧片段，保留近期原文。** 参考上游按 token 预算保留近期材料的做法，起始策略为可用消息预算的约 16%，支持固定 token 配置。工具调用与全部结果作为不可切开的组合；不得留下孤立结果。按明确标记处理运行时控制前缀，不假定旧摘要永远位于 index 1。
4. **旧摘要参加下一次汇总。** 新摘要替换旧摘要及选中的旧段，不再永久追加 `[本次补充]`。Todo 继续单独保留。更新摘要指令，消除“旧摘要由外部另行保存”的旧契约。
5. **确认缩小、确认保存，再交换。** 用同一口径检查新摘要（含包装）小于被替换段；空摘要、输出被 token 上限截断、没有可安全压缩区或未缩小均不伪报成功。摘要生成期间若模型投影变化，拒绝提交过时候选。复用 Conversation 的工具配对与持久化确认边界。
6. **统一入口。** 自动压力、手动 `/compact`、服务端上下文超限共用上述策略；模型切换时按目标窗口重新检查。保持有界恢复，不因压缩自动执行工具或重放未知副作用。

### 验收出口

- 长对话压缩后近期原文保持，工具调用/结果完整配对，系统前缀与 Todo 保持。
- 第二次压缩会重新整理旧摘要，不再无限追加；不缩小的候选不提交。
- 安全工具正文裁剪能够在不调用摘要模型时解除压力；原结果仍能按记录查回。
- 自动、手动、超限路径使用相同策略；摘要失败/取消/写入未确认仍保留停止，后台等待与迟到事件不被重放。
- 保存后关闭进程，重开恢复相同的摘要与近期尾部；源语义定向测试及本地合成模型入口通过。
- 涉及已有文件的改动可独立复核；真实模型质量与 Windows Terminal 体验按实际结果分别记录。

### 本方案的限制

不承诺压缩前全部 assistant 原文可逐字恢复。RuoCun 当前 checkpoint 以最新模型上下文为准；既有输入/工具记录与完整不可变会话转录是不同能力。
摘要热前缀复用需要结合各 provider 的工具/思考/图片投影核实；不能仅因附上工具定义就宣称缓存命中。

## 方案 B：核心策略，同时增加完整原文可回溯存储

包含 A，并将压缩前完整上下文/被替换区段持久化，提供摘要与原片段的引用关系及读取入口。
DeepSeek Harness 使用追加日志和可见历史投影实现这一点；RuoCun 不必照搬整套结构，但需要为归档、提交原子性、引用与恢复确定唯一权威。

该方案需要额外的存储格式/版本兼容决定及恢复验证。当前 SQLite 严格验证表结构，不能静默增加归档表冒充无迁移变更；也不能只写一个无确认的旁路文件就声称完整可恢复。
